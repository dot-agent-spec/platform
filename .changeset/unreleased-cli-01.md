"@dot-agent/cli": patch

`dot-agent unpack` wrote every archive file verbatim, including the `.description`, which still declares the *original* entry `.behavior` filename at its *original* location (e.g. `behavior main.behavior`) even though `pack` stores that file under `behaviors/main.behavior` in the archive and flattens the merge graph into a separate `agent.behavior` at the bundle root. The mismatch meant a subsequent `pack` over the unpacked directory couldn't find the name the description named and failed with `E012` ([#7](https://github.com/dot-agent-spec/platform/issues/7)). `unpack` now restores the *original source layout* instead: it parses the archived `.description` to find the entry's declared path, walks the merge graph from there exactly as `pack`'s own `consolidate()` does, and moves only the files that walk actually reaches back to their original root-relative path (their `behaviors/` prefix stripped) — the `.description` is left byte-for-byte as archived, since it already names the right file, which now exists where it says. `.agent/files.json`'s `behaviors` list is not used to decide what to restore: it also carries non-merge content that happens to live under `behaviors/` (a `teach`/`guide` reference, for instance), which the merge-graph walk correctly leaves alone. The flattened `agent.behavior` build artifact is dropped only once a real, restorable source has been confirmed to replace it — an entry genuinely named `agent.behavior` at the root gets the *original* (unflattened) source there instead, so an edit to the restored entry file reaches the next `pack`, and the two copies never collide. Anywhere this can't be established safely (the description doesn't parse, the entry isn't found under `behaviors/`, a merge target is missing, absolute, or would escape the agent root, or `.agent/files.json` is malformed or absent) falls back to extracting everything verbatim, exactly as unpack did before this fix existed.
